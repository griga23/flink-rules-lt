Flink Rules on Lightning Tables

A Process Table Function that applies filter, transform, alert and one-shot rules to a Faker IoT stream. The rules and the record of what already fired both live in Lightning Tables, and the PTF reads them once at startup. Tested on a live cluster in the <ENV_NAME> environment.

What we found

QuestionAnswer
Can a PTF call a service with a raw HttpClient?No Every call timed out (HttpConnectTimeoutException). Outbound traffic is blocked.
Can a PTF use a CREATE CONNECTION bound with USING CONNECTIONS?Works, undocumented It works in the PTF. The docs say external connectivity is only for scalar and table UDFs, so this may change.
Can Flink SQL join a Lightning Table directly?Not documented Lightning queries reject joins, subqueries and aggregates. The PTF calls the Lightning HTTP query API instead.
Does PTF state survive delete and recreate, same uid?No State belongs to the statement. The per-device device_seen counter restarts from 1.
How do one-shot rules survive a recreate?Fired history in Lightning rg_fired is loaded at startup and restores each (rule, device) count into state. No re-application was observed.

Architecture

The PTF (left) is Java: it loads the rules, keeps the per-device state and decides what fires. SQL (right) creates the tables, the connection and the function, calls the function in Statement 1, and runs the writer. The two meet only at the call in Statement 1 and the rows it gets back. The Kafka topics (bottom) hold the data: rg_rules and rg_fired are compacted topics that Lightning serves as tables, rg_processed is a plain topic.

  1. SQL Rules are written to rg_rules with INSERT INTO or any Kafka producer. Lightning ingests the compacted topic.
  2. PTF At startup open() reads the connection parameters. The first eval of each subtask scans rg_rules and rg_fired once with SELECT * through lightning_connection. If a scan fails the PTF throws; running without rules or history would silently re-fire one-shot rules.
  3. SQL Statement 1 passes the readings of rg_readings to the function, keyed by device_id, so each device has its own state.
  4. PTF The function evaluates the rules of the reading's sensor in priority order. On the first touch of a (rule, device) it restores the count and first-fired time from the loaded history into Flink state. A one-shot rule with a count above zero is skipped.
  5. PTF It returns rows: one FIRED row per rule that acted, then one RESULT row unless a FILTER dropped the reading. Statement 1 inserts them into the rg_processed topic.
  6. SQL The writer statement reads the rg_processed topic and keeps only FIRED rows.
  7. SQL It upserts them into rg_fired under the key rule_id|device_id. Lightning ingests the topic. The next statement incarnation reads it at step 2.

Rule semantics

A rule belongs to a rule_scope (the sensor type) and runs in priority order. All rules compare against the raw reading, not a transformed value. Disabled rules are not loaded, so a sensor with no enabled rule gets NO_RULE.

TypeparamsEffect
FILTER{"min":…,"max":…}Outside the range: action DROPPED, no RESULT row, later rules are not evaluated.
TRANSFORM{"fn":"C_TO_F"} or "HPA_TO_PSI"Sets value and unit. An unknown fn adds BAD_RULE:<id> to the status.
ALERT{"above":…}Raw value above the threshold sets alert = true.

one_shot rules act only the first time per (rule, device). Later readings get SKIPPED_ONE_SHOT:<rule_id> in the RESULT status. The example data in sql/32_generic_rules_data.sql:

SensorFilterTransform (one-shot)Alert
temperature-50 to 150°C to °Fabove 30
humidity0 to 100noneabove 85
pressure300 to 1100hPa to psiabove 1050
vibration0 to 50 (disabled)nonenone

The Faker source draws every reading uniformly from 0 to 1100, so most temperature and humidity readings are out of range and get dropped. That is a property of the test data, not of the PTF.

Delivery guarantees

Short version. Within one running statement the PTF state is exactly-once. One-shot rules are effectively once per (rule, device), with a duplicate window when the statement is rebuilt before a firing has reached rg_fired. The Faker source cannot be replayed, so end-to-end guarantees only apply to a real Kafka source.

Where a one-shot rule can still go wrong

  • Rebuild race (can fire twice). A firing travels PTF output topic, writer statement, rg_fired topic, Lightning ingestion. If the PTF statement is recreated before that finishes, the new statement does not see the firing.
  • 30-day window (can fire again). History rows whose last_fired is older than 30 days are ignored at startup, and state expires after 30 days. A (rule, device) idle for longer can fire again.
  • Startup failure is fatal by design. The PTF throws if a scan fails, so the statement fails or restarts instead of running blind.
  • Memory and size. Each scan is a single HTTP response with a 60 s timeout, no paging, and the whole fired table in the window is held in memory per subtask. Lightning response limits and retention were not tested.
  • Faker source. It generates new random rows on restart, so it does not replay. A Kafka source stores its offsets in the checkpoint.

To close the rebuild race, the PTF would have to write the fired record itself before emitting the row. A PTF has one output, so that needs a second output path or a sink the PTF controls, which was not built.

Recreate test and performance, 2026-11-23

A new statement rg-run-v3 with the same SQL and uid as the stopped rg-run-v2 was created at 08:19:09Z and ran for 9.5 minutes. The writer was not started, because it would replay the whole rg_processed topic into rg_fired. Evidence statements filtered rg_processed to rows from after the restart.

  • Startup: PENDING to RUNNING in 40 s. The first output row appeared about 55 s after creation.
  • State was reset: the first rows had device_seen between 1 and 62, while fire_count continued from the rg_fired history (for example 378 to 398 for r-hum-filter) and first_fired kept its old value.
  • No one-shot rule fired again: a filter for FIRED rows of the convert rules, or with fire_count = 1, read the 4,348-row backlog and then about 190 to 200 rows a minute, and produced 0 rows.
  • Every (device, sensor) pair skipped: a keep-first-row statement produced exactly 6 rows, one per device for temperature (SKIPPED_ONE_SHOT:r-temp-convert) and for pressure (SKIPPED_ONE_SHOT:r-press-convert). Temperature pairs appear later because the temperature filter drops about 86% of readings before the convert rule runs.
  • Count regression: r-temp-filter for dev-A was at fire_count 341 when the old run stopped and at 338 on the first row after the restart. That fits the rebuild race, where the last firings had not reached rg_fired. It does not change one-shot decisions, which only test for a count above zero. The cause was not isolated.

Rules version update, 2026-11-23

The rule r-temp-alert was changed from version 1 (alert above 30) to version 2 (alert above 100) with INSERT INTO rg_rules, an upsert on rule_id, at 09:02:52Z while rg-run-v4 was running. An evidence filter kept every r-temp-alert row with its rule_version and raw value. The temperature filter drops readings above 150, so alerts exist for raw values between the threshold and 150.

  • Running statement: no reload. For more than 4 minutes after the edit rg-run-v4 still emitted version 1, with raw values 34.39, 36.72, 38.74, 42.7, 62.75 and 70.08, all below the new threshold.
  • Recreated statement: the new version applies. rg-run-v5 (same SQL and uid) emitted version 2 only for raw values above 100, from 100.06 to 148.62. A filter for version 2 rows at or below 100 read 77 rows and emitted none.
  • Propagation: the recreated statement scanned about 6 minutes after the edit and already saw version 2. The actual time Lightning needs to ingest an edit was not measured.
  • Not checked: reading the rule row back from Lightning (the CLI used has no query command), an edit to a one-shot rule, and fire counts across a version change.

The rule was restored afterwards to version 1 so the table matches sql/32. Not yet tested: stop and resume of the generic statement.

Register the function (replace the artifact id) and run the PTF, then the writer:

CREATE FUNCTION apply_rules_generic AS 'demo.iot.ApplyRulesGenericPtf'
  USING JAR 'confluent-artifact://<ARTIFACT>'
  USING CONNECTIONS(`<ENV_NAME>`.`<CLUSTER_NAME>`.`lightning_connection`);

INSERT INTO rg_processed
SELECT event_kind, device_id, sensor_type, raw_value, `value`, unit, alert, rule_id,
       rule_version, action, fire_count, first_fired, event_ts, status, device_seen
FROM apply_rules_generic(
  input => TABLE rg_readings PARTITION BY device_id,
  env => '<ENV_ID>', cluster => '<CLUSTER_ID>',
  rulesTable => 'rg_rules', firedTable => 'rg_fired',
  uid => 'generic-v1');

INSERT INTO rg_fired
SELECT CONCAT(rule_id, '|', device_id), rule_id, rule_version, device_id, action,
       raw_value, `value`, fire_count, first_fired, event_ts
FROM rg_processed WHERE event_kind = 'FIRED';

Run order: 03_connection.sql, 30_generic_rules.sql, 31_generic_fired.sql, enable Lightning on both topics, 32_generic_rules_data.sql, 33_generic_io.sql, the function, 34_generic_run.sql, 35_generic_fired_writer.sql. Enable Lightning with confluent rtce rtce-topic create --cloud aws --region eu-central-1 --topic-name <topic> --environment <ENV_ID> --cluster <CLUSTER_ID>; the phase goes from PENDING to ACTIVE in one to three minutes.

status values on RESULT rows: OK, NO_RULE, SKIPPED_ONE_SHOT:<rule_id> and BAD_RULE:<rule_id>, joined by commas when several apply.

Things that cost us time

  • Column case in Lightning SQL. Unquoted column names fold to uppercase. Backticking a lowercase column in WHERE returns "Column not found". Leave columns unquoted; table names may be quoted.
  • scope is reserved in Flink SQL, hence rule_scope.
  • Updating the connection. ALTER CONNECTION … SET failed with "multiple authentication credentials". Drop and recreate it.
  • UDFs are immutable. Upload a new artifact, drop the function, recreate it with USING JAR and USING CONNECTIONS, then recreate dependent statements.
  • Global API key limit. Lightning needs a Global key, and the limit is 2 per user.
  • Reading results. The CLI cannot fetch SELECT results and confluent flink shell needs a TTY. The Confluent Cloud MCP server can read topics (consume_kafka_messages, no Kafka key needed), but it returns at most 10 of the newest messages per call and cannot filter. For exhaustive checks, write a filter statement's output to a small evidence topic.
  • Metrics lag. The Metrics API showed nothing for the first one to two minutes of a statement.
  • Statement start is slow. A new PTF statement took about 40 seconds from creation to RUNNING.
  • Statement names allow only lowercase letters, digits and hyphens, and must be unique, so a recreate needs a new name.
  • Expired CLI login makes polling loops spin silently. In zsh, keep flags in an array; an unquoted string variable is not split into arguments.

Before the next one-shot test. rg_fired still holds the firing history from today's runs. A new statement loads it at startup, so every one-shot rule is skipped from the first reading. For a clean test, write tombstones for its keys first, or point the PTF at a fresh fired table.
